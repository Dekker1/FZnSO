Implementing a solver means exporting [thirteen entry points](../../spec/entry-points/) from a dynamically loadable library.
The Rust and C++ bindings each provide a macro that writes all thirteen, leaving you the few methods that differ between solvers.

## Decide first

**Your solver's name**, which goes in every symbol (`fznso_gecode_solver_run`) and must match the library's file name: a valid C identifier not starting with `lib`.
See [Naming & versioning](../../spec/naming-and-versioning/).

**What you will declare.**
Start with all five capability lists empty and add as you go — declaring nothing is [conforming](../../spec/overview/#conformance) — remembering that declaring a [registry](../../registry/) name commits you to the registry's meaning.

## The methods that matter

Everything else is bookkeeping the macros handle.

- **`option_set` and `option_get`** — accept the options you declared, reject the rest with a message.
- **`run`** — read the model, search, report each solution, return a [status](../../spec/running/#status).
- **`statistic`** — report the solver-scoped statistics you declared, absent for anything else.

## Reading the model

The model is a callback table, not a structure.
Ask it what it holds:

```rust
for d in model.decisions() {
    let ty = d.ty();
    let domain = d.domain();       // absent if the variable has no explicit domain
    let wanted = d.in_solution();  // if true, every solution must assign it
}

for c in model.constraints() {
    match c.ident() {
        "int_lin_le" => post_lin_le(c.arguments()),
        // Anything you did not declare in `constraint_list` cannot reach you.
        other => unreachable!("undeclared constraint {other}"),
    }
}
```

Two rules govern everything you read, and both are [stated in full](../../spec/lifetimes-and-ownership/): ask a value its [`kind`](../../spec/types-and-values/#value-kinds) before reading it, and treat what you read as borrowed for the duration of `run`.

## Reporting

Call the solution callback once per solution.
**The values you hand it are borrowed from you**, so the storage behind them must outlive the call: build it before reporting, not inside the accessor.

Honour the two nullable callbacks.
A null [`on_message`](../../spec/running/#diagnostics) means skip *building* the diagnostic, not build it and discard it — both bindings expose this as a `wanted()` check — and a null [`should_stop`](../../spec/running/#stopping-early) means drop the poll from your search loop rather than call a predicate that always answers `false`.

## Failing

Return `FznsoError` from `run`, or a message from `option_set`; the caller then asks for the reason through `fznso_<name>_solver_read_error`.
Do not report failures through `on_message`, which is for diagnostics the search survived.

## Checking your work

The test consumer exercises the whole interface — options, statistics, solutions, messages, early stopping, and a model published back across the interface and compared against the original:

```sh
just test-cpp                                  # builds and runs test_consumer
./target/test_consumer /path/to/libmysolver.so
```

If your solver is in Rust, run the suite under miri as well.
Every bug in the handle-casting class this interface can produce passed the ordinary test suite first.
